The game loop

2D track · lesson 1 of 6 · about 20 minutes

Every game is the same three lines repeated forever: read input, update the world, draw it. The hard part is time.

1 The idea

Screens refresh 60, 120 or 144 times a second, and frames never arrive perfectly evenly. If your game moved the player "a little each frame", it would run twice as fast on a 120 Hz (hertz) screen, and physics would behave differently on every computer.

Kindling updates the world in fixed steps of 1/60 of a second. Each frame, the real time that passed goes into an accumulator. While the accumulator holds at least one step, we run a step and take it out. Whatever is left is less than one step; divided by the step size it gives alpha, a number from 0 to 1 that says how far we are toward the next step, which you can use to draw smoothly.

One more rule: if the tab freezes for two seconds, we do not try to run 120 steps at once (that can freeze the game again, the "spiral of death"). Frame time is clamped to a quarter of a second.

2 See it

Frames (top) arrive unevenly; steps (dots) are perfectly even. Raise the frame jitter and watch the accumulator bar fill and empty while the steps stay even.

Open it in its own tab (easier on a phone).

3 Walkthrough

  1. The loop is engine/core/loop.js. Its heart is advance(frameSeconds): 
    function advance(frameSeconds) {
  accumulator += Math.min(frameSeconds, maxFrameSeconds);   // clamp long freezes
  while (accumulator >= stepSeconds) {
    update(stepSeconds);                                    // always the same size
    accumulator -= stepSeconds;
  }
  render(accumulator / stepSeconds);                        // alpha: 0..1
}
  2. Because advance takes the time as an argument instead of reading the clock, the tests can feed it exact numbers. Look at tests/checks/core.checks.js: feeding 3.5 steps of time runs exactly 3 updates and leaves alpha at 0.5.
  3. In a real game you rarely call the loop yourself. createGame() makes one and calls your scene's update(game, stepSeconds) and render(game, context, alpha): 
    game.scenes.add("play", {
  update(game, stepSeconds) {
    ball.x += ball.speed * stepSeconds;   // pixels per second x seconds = pixels
  },
  render(game, context) {
    fillCircle(context, ball.x, ball.y, 4, "white");
  },
});
  4. Speeds are always per second and multiplied by stepSeconds. Then changing the step size (try stepSeconds: 1 / 30 in createGame) changes smoothness, not how fast the game plays.

4 Exercise

Make a new folder samples/my-first-loop/ with an index.html (copy one from samples/00-hello/ and keep its import map) and a main.js. Draw a 16×16 square that moves right at 80 pixels per second and wraps around to the left edge when it leaves the 320-pixel-wide screen. Show the frames per second in the corner.

Hint 1

wrap(value, min, max) from kindling/math/scalar.js does the wrapping.

Hint 2

game.time.fps holds the frames per second. Draw it with text() from kindling/2d/draw.js.

Solution

One way to do it (yours can be different and still right):

import { createGame } from "kindling/game.js";
import { fillRect, text } from "kindling/2d/draw.js";
import { wrap } from "kindling/math/scalar.js";

const game = createGame({ width: 320, height: 180 });
const square = { x: 0, y: 82 };

game.scenes.add("play", {
  update(game, stepSeconds) {
    square.x = wrap(square.x + 80 * stepSeconds, -16, 320);
  },
  render(game, context) {
    fillRect(context, square.x, square.y, 16, 16, "#ffb347");
    text(context, "fps " + game.time.fps, 4, 4, { color: "#8a8f9c" });
  },
});
game.start("play");
